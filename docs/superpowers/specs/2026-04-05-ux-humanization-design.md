# UX 人性化改造设计文档

**日期**：2026-04-05  
**方向**：方案 B — 分模块递进优化  
**核心约束**：所有改动只动展示层（文案 / 样式 / 动效 / 条件渲染），不改数据结构、API 调用逻辑、路由配置、store 核心逻辑。

---

## 一、背景与目标

当前平台功能完整，但交互语言过于系统化、公式化，缺乏"有人在场"的服务感。目标参照国内优秀代练平台（如东东电竞）的体验质感，在不破坏现有功能的前提下，让用户感受到：**我被认真对待，而且这里的人懂我**。

**语气基准**：专业有温度，像海底捞服务员——不冷漠、不官僚，也不轻浮。

---

## 二、全局语言规则

### 2.1 服务类型称呼

| 服务类型 | 称呼 | 本质区别 |
|----------|------|----------|
| 代练 | 代练 | 代练上老板的号替老板打 |
| 陪玩 | 陪玩 | 用自己的号与老板组队同玩 |
| 教学 | 教学（归属陪玩类） | 用自己的号陪新手边玩边学 |

- 禁止使用"大神"作为通用称呼
- 禁止使用"教练"
- 陪玩和教学可统称"陪玩"，需要区分时按场景标注"教学陪玩"

### 2.2 代练师双重身份

同一代练师账号在不同场景使用不同语境：

| 代练师所在场景 | 身份 | 使用语境 |
|----------------|------|----------|
| 管理自己发布的服务、接单 | 服务提供方 | "我的接单"、"接单中"、"发布服务" |
| 自己花钱购买他人服务时 | 老板 | 与普通用户完全相同的语言 |

前端已有 `isBooster` + 页面上下文判断，直接复用，不新增逻辑。

### 2.3 通用文案替换表

| 场景 | 当前（系统感） | 改后（服务感） |
|------|--------------|--------------|
| 加载中 | 加载中 | 正在帮你找… |
| 空状态 | 暂无数据 | 还没有记录，去看看吧？ |
| 提交成功 | 操作成功 | 搞定了 |
| 请求失败 | 请求失败，请重试 | 出了点小问题，再试一次？ |
| 返回按钮 | 返回 | 返回 （保持，不要过度改） |

## 三、板块一：设计语言基准

### 3.1 文案原则

1. **字越少越有力**——能用词就不用句，不堆砌引导语
2. **每个状态都有"人在场"的感觉**——等待不是空屏，操作后有即时反馈
3. **反馈要有情绪，但不夸张**——完成是"搞定了"不是"恭喜您"

### 3.2 交互原则

1. **流程要有进度感**——多步操作让用户知道自己在哪一步、还剩什么
2. **状态变化要主动告知**——不依赖用户刷新，前端轮询已有，只加展示层反馈
3. **错误提示帮用户，不指责用户**——"还差一步" 不是 "此字段必填"

## 四、板块二：首页入口

### 4.1 文案改造

**英雄区问候语**（根据时段动态切换，纯前端计算）：

| 时段 | 文案 |
|------|------|
| 06:00–11:00 | 早上好，今天先冲一把？ |
| 11:00–18:00 | 下午了，找个代练上分？ |
| 18:00–24:00 | 今晚要上分还是陪玩？ |
| 00:00–06:00 | 还没睡？来一把放松一下 |

**服务模式选择**：

| 当前 | 改后 |
|------|------|
| 代练上分 | 帮我上分（代练上你的号） |
| 陪玩 | 一起玩（找个陪玩搭子） |
| 教学 | 带我学（教学陪玩） |

**进入按钮**根据选中模式变化：
- 选代练 → `找代练上分 →`
- 选陪玩 → `找陪玩搭子 →`
- 选教学 → `找教学陪玩 →`

**搜索框占位文字**：`想打什么？搜游戏或者服务都行`

**游戏卡片副标题**（利用现有数据）：`今天已有 N 笔订单 · X 位代练在线`

### 4.2 交互改造

| 交互点 | 改造内容 |
|--------|----------|
| 游戏卡片在线指示 | 有代练在线的游戏显示绿色脉冲小点 |
| 游戏切换过渡 | 旧内容淡出下移，新内容淡入，0.25s |
| 游戏卡片 hover | 轻微上浮 + 显示"今日最热服务"一行 |

## 五、板块三：服务卡片

### 5.1 文案改造

**卡片信息重组**（信息量不变，排布逻辑从"商品"改为"认人"）：

```
[在线 · 通常 3 分钟内接单]          ← 状态行
已完成 128 单  ·  好评率 98%         ← 信任行
¥45 / 小时                           ← 价格行
"打法稳健，不浪，适合想保胜率的玩家"  ← 个人签名（代练师填写）
[找他代练] / [找他陪玩]              ← CTA，按服务类型显示
```

**服务类型标签**：

| 当前 | 改后 |
|------|------|
| 代练 | 帮你上号代打 |
| 陪玩 | 组队一起玩 |
| 教学 | 教学陪玩 |

**价格加上下文**：`¥45/小时 · 今日已接 4 单`

**CTA 按钮**按服务类型区分：
- 代练服务 → `找他代练`
- 陪玩服务 → `找他陪玩`
- 代练师不在线 → `预约他`（功能不变，只改文案）

**筛选栏**：

| 当前 | 改后 |
|------|------|
| 价格区间 | 我的预算 |
| 服务类型 | 我想要 |
| 游戏 | 打哪个 |

筛选后结果提示：`找到 23 位代练，现在都可以接单`

### 5.2 交互改造

| 交互点 | 改造内容 |
|--------|----------|
| 在线状态 | 绿点+文案"在线，可立即接单" / 灰点+"2小时前活跃" |
| 卡片 hover | 轻微放大 + 展示个人签名一行 |
| CTA hover | 背景轻微变亮，文案变 `立即找他` |

## 六、板块四：下单流程

### 6.1 文案改造

**分步骤对话式引导**（三步，后端接口不变，前端拆步收集后一次提交）：

**第 1 步：你要打什么？**
- 字段：游戏 + 服务类型
- 服务类型选项文案：`代练上号` / `陪玩` / `教学陪玩`

**第 2 步：你的情况是？**
- 字段标签：`现在几段` / `想冲到哪` / `打哪个服务器`

**第 3 步：确认发布**
- 字段：预算 + 备注（`还有什么想告诉代练的？`，选填）
- 预览卡片：展示用户填写的需求摘要
- 提交按钮：`发布代练需求` / `发布陪玩需求`（按选择类型动态显示）

**提交成功提示**：
```
需求发出去了，等代练接单    （代练场景）
需求发出去了，等陪玩接单    （陪玩场景）
```

**错误提示**：`还差一步 — [具体缺少什么]`，不用"此字段必填"

### 6.2 交互改造

| 交互点 | 改造内容 |
|--------|----------|
| 步骤进度条 | 顶部显示当前步骤，1/3 → 2/3 → 3/3 |
| 提交动效 | 按钮变为"✓ 已发出"短暂停顿，再跳转订单详情 |
| 第3步预览卡 | 展示需求卡片预览，确认后再发布 |

## 七、板块五：订单状态页

### 7.1 文案改造

**状态标签替换**：

| 状态 | 代练场景 | 陪玩场景 |
|------|----------|----------|
| PENDING | 等待代练接单 | 等待陪玩接单 |
| LOCKED | 代练上号中 | 陪玩进行中 |
| COMPLETED | 代练完成了！| 这局打完了！|
| CANCELLED | 订单已取消 | 订单已取消 |
| PAID | 款项已到位，代练可以开始了 | 款项已到位，陪玩可以开始了 |

**PENDING 状态补充信息**（纯前端展示）：
```
你的需求已发出
代练们正在看你的订单
```

**代练场景专属提示**（LOCKED 状态下）：
```
代练正在使用你的账号上分
```

**聊天入口**：
- `联系代练` / `联系陪玩`（按订单类型显示）
- `问问进度` （副文案）

**评价区域**：
- 评价入口：`说说这次体验`
- 评价提交后：`谢谢，你的反馈会帮助更多人找到靠谱的代练`

### 7.2 交互改造

| 交互点 | 改造内容 |
|--------|----------|
| 状态时间线 | 纵向时间线串联所有状态节点，替代单一状态标签 |
| PENDING shimmer | 等待区域加 CSS 扫光动效，配合"等待中"文案 |
| 接单成功提示 | 状态变 LOCKED 时，顶部滑出绿色提示条 |
| 完成确认按钮 | `确认，代练完成了` → 变绿 + "✓ 已确认" → 出现评价区 |

## 八、实现约束总结

1. **只动展示层**：文案 / 样式 / CSS 动效 / 条件渲染，不改数据结构和 API
2. **复用现有状态**：`isBooster`、订单状态字段、服务类型字段直接复用
3. **不新增接口**：PENDING 页的"代练们正在看"为纯前端文案，不需要真实浏览数据
4. **分模块交付**：按首页 → 服务卡片 → 下单流程 → 订单状态页顺序实现，每个模块独立可上线
